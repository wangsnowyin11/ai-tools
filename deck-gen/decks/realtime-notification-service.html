Realtime Notification Service

One shared push pipeline: sub-second in-app notifications, no more client polling

Problem & goals

Six teams poll for notifications separately: slow, wasteful, and duplicated.

Today

  • ~40k QPS — wasted client polling traffic
  • Up to 30s — notification delay
  • 6 copies — same logic rebuilt per team

Goals

  • < 1s p99 — delivery to online clients
  • > 90% — reduction in polling traffic
  • At-least-once — clients dedupe by ID
  • One SDK — shared by every product team

Out of scope: email and push delivery, rich templating (phase 2).

Architecture

Kafka decouples producers; Presence routes each event to the right WebSocket gateway.

flowchart LR
  prod["Product services"] --> pub["Publish API"]
  pub --> kafka(["Kafka topic"])
  kafka --> fan["Fanout workers"]
  fan --> pres[("Redis Presence")]
  fan --> inbox[("Cassandra Inbox")]
  fan -->|"gRPC"| gw["Gateway nodes"]
  gw -->|"WebSocket"| client["Clients"]
  1. Publish API — validates the schema and rate-limits each producer
  2. Kafka — partitioned by user_id, so ordering holds per user
  3. Fanout — writes to Inbox, then looks up the user in Presence
  4. Gateway — about 200k sockets per node; pushes to the client

Delivery flow

Live push when the user is online; Inbox catch-up guarantees eventual delivery.

sequenceDiagram
  participant C as Client
  participant G as Gateway
  participant F as Fanout
  participant I as Inbox
  C->>G: Connect with session token
  G->>G: Register in Presence, 60s TTL
  F->>I: Store event
  F->>G: Forward if online
  G->>C: Push over WebSocket
  C-->>G: ACK, retried up to 3x
  C->>I: On reconnect, GET inbox since cursor
  1. Connect — gateway registers user to node; heartbeats refresh the TTL
  2. Store first — every event lands in Inbox (30-day TTL)
  3. Push and ACK — unACKed events retry 3 times
  4. Catch up — reconnecting clients read Inbox, then go live

Alternatives & risks

WebSocket plus our own fanout beats the alternatives on latency, ACKs, and cost.

Option / riskWhy not / mitigation
Longer pollingCheap, but delays get worse and duplication stays
Server-Sent EventsNo client ACK channel; weaker mobile support
Managed pub/subAbout 3x the cost at our scale; data residency concerns
Reconnect stormsJittered reconnects plus connection draining on deploy
Hot partitionsCap fanout per event; separate broadcast path

Rollout Milestones & Requirements

Three milestones from staging to all six teams by Q1.

  • M1 · Nov — Gateway and Presence in staging; internal dogfood
  • M2 · Dec — two pilot teams behind a flag, 5% of traffic
  • M3 · Q1 — all six teams migrated; client polling deprecated
  • Capacity — about 40 gateway nodes for 8M peak connections, plus 25% headroom

Decisions needed: per-team quotas at launch? Long-term owner of the client SDK?
